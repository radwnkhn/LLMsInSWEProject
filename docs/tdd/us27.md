## Tests first

The acceptance criteria were agreed first and committed in `docs/User_Stories_and_Acceptance_Criteria.md`
and `issues/create_github_issues/issues.py`. The tests were then written and committed on their own
(`Add failing US-27 usage and moderation tests (red)`) before any production change, and run against the
existing app. They use the in-memory repository, storage and auth, plus a disposable local Postgres for the
repository contract. No Supabase project is called.

### Tests changed during the green phase

- **`us27_choosing_dates_reloads_usage_and_uploads`.** Its mocked usage API always answered with the
  default range and ignored the dates it was asked for. A real server echoes the requested range back,
  and the page follows whatever range the server reports. The mock now echoes the dates.
- **`us27_shows_signups_and_uploads_per_day_with_totals`.** The day table now lists the newest day first.
  The phone-width screenshot showed that oldest-first hid the recent days below the table's scroll. The
  test's row order was updated to match.

## Implementation

- **One deletion path (`backend/app/deletion.py`).** The US-21 upload deletion moved out of the
  `DELETE /uploads/{id}` handler into `upload_media_paths()` and `delete_upload_with_media()`. Both the
  owner's delete and the admin's removal call it: storage first, then the database rows (analyses,
  measurements, AI attempts, validator errors and ratings cascade). A test checks that both endpoints use
  this one function.
- **Removal (`POST /admin/uploads/{id}/remove`).**
  - It needs `{"confirmed": true, "reason": "off_topic" | "inappropriate" | "other"}`, and an optional
    `note` of up to 200 characters.
  - It holds the owner's lock and refuses while an analysis is queued or processing (409), as US-21 does.
  - It writes the moderation log entry first, then deletes. If deletion fails, the entry is removed and the
    API returns 502, so the admin can retry.
- **Moderation log.** Migration `20261113000000_us27_moderation.sql` creates `public.moderation_log` with
  the upload ID, analysis IDs, lift, owner, admin, reason, note and time.
  - There is no foreign key to the upload, which is deleted. User references are `on delete set null`, so
    entries survive account deletion.
  - RLS is on, with an admin-read policy. The migration also adds indexes for time ranges.
  - `GET /admin/moderation-log` lists entries newest first, with emails resolved at read time.
- **What the owner sees.** For an ID in the moderation log, the owner's analysis endpoints return 410 with
  "This upload was removed by a moderator. Reason: …". That covers results, retry, feedback and
  comparisons. Anyone else still gets 404, so nobody can probe for removed IDs. The results page shows the
  message and a "Back to history" link instead of the error and Retry box.
- **Usage (`GET /admin/usage`).**
  - It reports sign-ups (user records gain `created_at`, which Postgres already stored) and uploads per UTC
    day, zero days included, with totals and the number of removals in the range.
  - The range defaults to the last 30 days and shares the date parsing and validation of the US-26 cost
    summary, moved into `_report_range()`.
- **Upload list (`GET /admin/uploads`).** Uploads are listed newest first with owner, lift, filename, the
  newest analysis (after a retry) and its status. Filters are `start`, `end` and `lift`; with no dates, the
  list covers every upload.
- **Frontend.**
  - `/admin/moderation` ("Usage and moderation", linked from the admin page) has a usage section with
    From and To dates, the upload list with a Lift filter, Analysis links and Remove buttons, and the
    moderation log.
  - The removal dialog reuses the US-21 `DeleteConfirmation` dialog, which keeps its focus handling,
    Escape, Cancel and error display. It gained optional wording, a confirm-disabled state and a slot for
    the reason picker.

## Assumptions

- **Removal deletes rather than hides.** It reuses the US-21 deletion as asked, so a removed upload's
  analyses, measurements, AI attempts and ratings are deleted, not hidden. They also leave the US-26 cost
  figures and the US-27 usage counts. The moderation log keeps the removal's own record, and the usage page
  counts removals separately.
- **The log keeps only what explains the removal:** IDs, lift, the two accounts, the reason, an optional
  note and the time. It keeps no video, measurements or AI output.
- **Who sees "removed by a moderator".** Only the owner, and only while their account exists. Other users
  get the same 404 as for any unknown ID.
- **Reasons** are a fixed list: off-topic, inappropriate, other. The optional note is kept only for
  "other", where it helps explain the removal.
- **Days** are UTC dates. "Sign-ups" means user records created in the range, and "uploads" means stored
  uploads created in the range. The placeholder's "active users" figure wasn't in the agreed criteria and
  was left out.
- **Uploads that are still processing** can't be removed until they finish, the same rule as US-21.
- **The removal dialog** names the owner's email and the lift, so the admin can be sure they picked the
  right upload.
